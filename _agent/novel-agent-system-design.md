# 小说 Agent 与 Skill 系统规划文档

日期：2026-06-25  
适用范围：`/Users/yao/Documents/小说项目`

## 1. 文档目的

本文件用于规划一个服务多本小说创作的 agent 与 skill 系统。当前根目录不是某一本小说的专属目录，而是一个长期使用的小说创作工作区。

本轮规划只处理以下问题：

- 如何组织根目录，使其能同时承载多本小说。
- 如何把 Codex/Agent 调整成小说创作工作台。
- 需要哪些 skill，以及每个 skill 的职责边界。
- 如何让一本小说从立项、设定、纲要、正文、审校到导出形成稳定流程。
- 哪些能力需要后续自定义封装，哪些能力只需通过文档规则约束。

本轮不处理以下问题：

- 不判断具体小说类型。
- 不展开任何具体世界观。
- 不写正文。
- 不替某一本小说做人物、剧情或章节设计。

## 2. 总体原则

### 2.1 Skill 负责流程，小说项目负责内容

Skill 里不应写入某本小说的专属设定、人物关系或世界观。Skill 只定义工作方法，例如如何归档设定、如何写章纲、如何检查时间线、如何回写角色状态。

每一本小说的具体内容都保存在该小说自己的目录中，由 agent 在任务开始时读取。

### 2.2 根目录是工作台，不是单本小说

根目录应放置跨项目的规则、模板、skill 草案、调研资料和共用流程。每一本小说应作为根目录下的独立子项目存在。

### 2.3 长篇创作依赖文件记忆，不依赖模型临场记忆

长篇小说最容易出现的问题是设定漂移、人物状态错乱、伏笔遗忘和时间线冲突。因此，agent 每次工作前必须读取项目文件，每次完成阶段性输出后必须回写状态。

### 2.4 先建立管理能力，再建立写作能力

第一阶段不急于封装“自动写正文”的 skill。应优先建立：

- 工作区路由能力。
- 新小说初始化能力。
- 小说资料库管理能力。
- 状态回写和一致性检查能力。

写作型 skill 应在项目结构稳定后再封装。

说明：

- `小说A/`、`小说B/`：每本小说独立管理，互不串设定。

## 5. Agent 总体架构

该系统建议采用“总控 agent + 专项 skill”的结构。

```text
用户输入
  ↓
novel-workspace-router
  ↓
判断任务类型
  ↓
调用对应 skill
  ↓
读取当前小说项目文件
  ↓
执行任务
  ↓
输出结果
  ↓
必要时回写状态文件
```

总控 agent 的职责：

- 判断当前任务属于工作区规划、创建新小说、整理设定、写大纲、写正文、审校、查资料还是导出。
- 判断当前任务是否需要进入某一本小说目录。
- 防止不同小说之间的设定互相污染。
- 在信息不足时要求用户先明确目标，而不是擅自补设定。
- 在执行写作任务前，确认必要资料是否存在。

## 6. Skill 清单与职责边界

### 6.1 novel-workspace-router

用途：作为整个小说工作区的入口 skill。

触发场景：

- 用户在根目录提出小说相关任务。
- 用户没有明确指定某本小说。
- 用户要求规划、初始化、整理、检查或写作。

职责：

- 判断任务属于“工作区级”还是“单本小说级”。
- 如果是单本小说任务，定位目标小说目录。
- 如果目标小说不存在，引导使用 `novel-project-initializer`。
- 如果任务跨多本小说，要求用户明确范围。

不负责：

- 不写正文。
- 不生成具体剧情。
- 不替用户决定小说类型。

### 6.2 novel-project-initializer

用途：创建一本新小说的标准目录和初始文件。

触发场景：

- 用户说“新建一本小说”。
- 用户在根目录提供一个新书名或新项目设想。
- 用户希望把已有零散资料整理成新小说项目。

职责：

- 创建单本小说目录结构。
- 生成初始说明文件。
- 建立设定、角色、剧情、正文、状态快照等目录。
- 根据用户已有信息填入初稿，不编造缺失内容。

不负责：

- 不写完整大纲。
- 不生成正文。
- 不做市场定位判断，除非用户明确要求。

### 6.3 novel-bible-manager

用途：管理小说圣经，包括世界观、规则、角色、势力、地点和术语。

触发场景：

- 用户提供世界观或设定。
- 用户要求整理人物关系。
- 用户要求检查设定是否冲突。
- 用户要求把口述想法变成可长期维护的资料库。

职责：

- 把零散设定归档到正确文件。
- 区分“已确认设定”“待确认设定”“灵感草稿”。
- 维护术语一致性。
- 记录设定来源和变更。

不负责：

- 不擅自把灵感草稿升级为正式设定。
- 不因写作需要随意改动规则系统。

### 6.4 novel-plot-architect

用途：设计和维护剧情结构。

触发场景：

- 用户要求写全书大纲、卷纲、章纲。
- 用户要求梳理主线、支线、伏笔、冲突链。
- 用户要求检查剧情推进是否合理。

职责：

- 把剧情拆成主线、支线、阶段目标和章节节点。
- 维护伏笔表、冲突链和时间线。
- 检查因果是否成立。
- 标记悬而未决的问题。

不负责：

- 不直接写正文。
- 不把市场套路强加给用户风格。

### 6.5 novel-draft-writer

用途：根据已确认资料写正文草稿。

触发场景：

- 用户要求写某一章、某一场景、某段对白。
- 目标小说已经有必要的设定、角色状态和章纲。

职责：

- 读取当前章纲、角色状态、事实快照和风格要求。
- 按指定范围写正文。
- 输出后提示需要回写的状态变化。

不负责：

- 不跳过章纲直接长篇发挥，除非用户明确要求即兴创作。
- 不私自改变核心设定。

### 6.6 novel-continuity-checker

用途：检查一致性。

触发场景：

- 用户要求审校章节。
- 用户担心设定冲突。
- 用户要求检查角色状态、时间线、伏笔是否错乱。

职责：

- 检查人物是否知道不该知道的信息。
- 检查地点、时间、伤势、物品、能力、关系是否连续。
- 检查伏笔是否被遗忘或提前暴露。
- 输出问题清单和修复建议。

不负责：

- 不直接重写全文，除非用户授权。

### 6.7 novel-style-keeper

用途：维护文风和表达边界。

触发场景：

- 用户提供风格样本。
- 用户要求去 AI 味。
- 用户要求保持某种叙事口吻。
- 用户要求统一对白、节奏或句式。

职责：

- 建立风格样本库。
- 提炼常用句式、禁用表达、叙述密度、对白习惯。
- 对草稿做风格一致性检查。

不负责：

- 不把所有文本磨成同一种腔调。
- 不牺牲角色差异。

### 6.8 novel-revision-desk

用途：修订和增强文本。

触发场景：

- 用户要求润色、压缩、扩写、增强张力。
- 用户要求改对白、改节奏、改场景。
- 用户要求把草稿打磨成可发布版本。

职责：

- 保留原意进行修订。
- 标记重大改动点。
- 区分语言润色、结构调整和剧情改写。

不负责：

- 不在未说明的情况下改变剧情结果。

### 6.9 novel-research-scout

用途：做资料检索、扫榜和外部参考整理。

触发场景：

- 用户要求检索资料。
- 用户要求参考某类题材、榜单、平台趋势或现实知识。
- 用户要求调研 GitHub、写作方法或工具链。

职责：

- 检索公开资料。
- 标记来源和日期。
- 把资料整理为参考，不直接写进正式设定。
- 区分事实资料、竞品观察和创作灵感。

不负责：

- 不把未经确认的网络资料写入小说圣经。

### 6.10 novel-export-packager

用途：导出和整理成果。

触发场景：

- 用户要求导出 docx、pdf、epub。
- 用户要求整理投稿版、存档版或平台发布版。

职责：

- 根据目标格式整理章节。
- 生成目录、标题、正文格式。
- 输出可交付文件。

不负责：

- 不修改正文内容，除非用户同时要求排版修订。

## 7. 核心工作流

### 7.1 创建新小说

```text
用户：新建一本小说，名字叫 X
  ↓
novel-workspace-router 判断为新项目任务
  ↓
novel-project-initializer 创建目录
  ↓
生成初始文件
  ↓
等待用户提供具体设定
```

### 7.2 整理设定

```text
用户提供零散设定
  ↓
novel-bible-manager 分类
  ↓
写入对应资料库
  ↓
区分已确认、待确认、灵感草稿
  ↓
更新事实快照
```

### 7.3 写大纲

```text
用户要求设计大纲
  ↓
novel-plot-architect 读取项目总纲和设定资料库
  ↓
生成或修订全书大纲、卷纲、章纲
  ↓
更新伏笔表、冲突链、时间线
```

### 7.4 写正文

```text
用户要求写某章或某场景
  ↓
novel-draft-writer 读取章纲、角色状态、事实快照、风格要求
  ↓
生成正文草稿
  ↓
列出本章产生的状态变化
  ↓
用户确认后回写状态快照
```

### 7.5 审校与修订

```text
用户要求检查或润色
  ↓
novel-continuity-checker 检查设定和连续性
  ↓
novel-style-keeper 检查文风
  ↓
novel-revision-desk 执行修订
  ↓
记录审校结果
```

## 8. 状态与记忆机制

为避免长篇创作漂移，每本小说至少维护以下状态文件：

- `06_状态快照/当前上下文.md`
- `06_状态快照/事实快照.md`
- `06_状态快照/角色状态快照.md`
- `06_状态快照/未解决伏笔.md`
- `06_状态快照/已确认设定.md`

状态文件原则：

- 正文生成前必须读取。
- 正文生成后不得自动回写重大变化，应先列出变化让用户确认。
- 已确认设定优先级高于灵感草稿。
- 用户临时想法不能覆盖正式设定，除非明确说“更新设定”。

## 9. GitHub 与外部项目参考策略

调研中发现的公开项目可作为设计参考，但不建议第一阶段直接依赖。

参考方向：

- `worldwonderer/oh-story-claudecode`：参考其中文网文 skill 包和多 agent 分工。
- `ExplosiveCoderflome/AI-Novel-Writing-Assistant`：参考完整 AI 小说生产流程。
- `zy-zmc/tianming-novel-ai-writer`：参考状态回写与创作上下文管理。
- `iLearn-Lab/NovelClaw`：参考记忆层和长篇一致性管理。
- `ydsgangge-ux/dramatica-flow`：参考剧情因果链、伏笔和关系图管理。
- `vkbo/novelWriter`、`olivierkes/manuskript`、`Zettlr/Zettlr`：参考传统写作软件的信息组织方式。

采用原则：

- 只吸收工作流思想，不直接混入复杂框架。
- 不让外部项目决定本工作区目录结构。
- 不引入大型依赖，除非后续确实需要可视化、数据库或自动导出。

## 10. 第一阶段交付目标

第一阶段建议只完成三件事：

1. 建立 `_agent/` 规则文档。
2. 建立 `_templates/novel-project-template/` 单本小说模板。
3. 起草首批三个 skill：
   - `novel-workspace-router`
   - `novel-project-initializer`
   - `novel-bible-manager`

这三个 skill 能解决最基础的问题：

- 根目录不会和单本小说混淆。
- 新小说可以稳定创建。
- 世界观和设定不会散落在聊天记录里。

## 11. 第二阶段交付目标

第二阶段再封装以下 skill：

- `novel-plot-architect`
- `novel-continuity-checker`
- `novel-style-keeper`

这阶段解决的是“长篇能不能稳住”的问题：

- 剧情推进有结构。
- 伏笔和时间线可追踪。
- 人物状态不漂移。
- 文风能被持续维护。

## 12. 第三阶段交付目标

第三阶段再封装输出型能力：

- `novel-draft-writer`
- `novel-revision-desk`
- `novel-research-scout`
- `novel-export-packager`

这阶段才开始强化正文生产、修订和导出。

## 13. 后续实施顺序

建议按以下顺序推进：

1. 完成本规划文档。
2. 编写 `_agent/operating-rules.md`，明确本工作区的通用工作规则。
3. 创建 `_templates/novel-project-template/`。
4. 起草 `novel-workspace-router` skill。
5. 起草 `novel-project-initializer` skill。
6. 起草 `novel-bible-manager` skill。
7. 用一个虚拟小说项目测试初始化和资料归档流程。
8. 根据测试结果修订 skill。

## 14. 当前决策

当前已确认：

- 根目录是多小说工作区。
- 本轮只规划 agent 与 skill。
- 具体小说内容未来在根目录下另建子项目。
- 第一阶段优先做管理型 skill，不急于写作型 skill。

待确认：

- `_skills/` 中的 skill 是先作为本项目内草案维护，还是直接安装到 Codex 全局 skill 目录。
- 单本小说模板是否需要支持多语言命名或固定中文命名。
- 是否需要为每本小说启用 git 版本管理。
- 是否需要把参考资料、拆文库和市场调研严格隔离。
